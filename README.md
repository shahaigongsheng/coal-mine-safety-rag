# 煤矿安全标准智能问答系统

> 自然语言提问 → 返回**条文原文** + **出处（文件名 / 标准号 / 条号 / 页码）**
> 语料来自本地的矿山安全标准原始资料 1084 份候选，构建出 5.6 万条可溯源的规范条文。

针对工业标准文档的三类现实问题而建：**监管文本长、条款指代强、扫描件与 CID 乱码 PDF 占比高**。
系统全程可离线运行 —— 不配任何 API key 也能用（纯检索模式，答案即为原文，不会编造）。

---

## 一、它能做什么

| 功能 | 说明 |
|---|---|
| 原文问答 | 提问返回规范条文原句，**不做改写**，杜绝幻觉 |
| 精确溯源 | 每条结果标注 文件 / 标准号 / 条号 / 页码 / 章节路径 |
| 条款直查 | 输入「第二百五十一条」直接锁定该条，不被分词打散 |
| 扫描件可用 | PDF 无文本层或字体乱码时自动转 OCR |
| 离线可跑 | 无 LLM、无向量模型时仍可检索（BM25 单路） |
| 一键重索引 | 增量抽取，几秒重建 |

## 二、架构

```
raw 原始文件（PDF/DOCX/DOC/MD）
        │
        ▼  src/extract.py       抽取 + 质量判定 + OCR 兜底 → data/extracted/*.json
        ▼  src/clean.py         去页眉页脚 / 合并断行 / 全角归一
        ▼  src/split.py         按「第X条 / X.X.X / 附录」切条 → data/clauses.jsonl
        ▼  src/retrieve.py      BM25 + 向量 + 条款精确路 → RRF 融合 → 多样性重排
        ▼  app/streamlit_app.py 前端展示原文 + 出处高亮
```

### 各模块「原理 / 作用」对照

| 模块 | 原理 | 作用 |
|---|---|---|
| 文本质量判定 | 按中文字符占比 + 非常见字符占比区分：正常 / CID 乱码 / 扫描件 | 决定该文件走直读还是 OCR，避免把乱码灌进索引 |
| 页眉页脚剔除 | 统计每页首尾行的出现频次，≥60% 且长度≤40 字判为噪声 | 去掉反复出现的书名页码，减少假命中 |
| 断行合并 | 行末无结束标点且下一行非新条款 ⇒ 判定为换行而非分段 | 把 PDF 拆碎的句子还原成完整条文 |
| 条款切分 | 以「第X条」「5.2.3」「附录A」为锚点切出最小可引用单元 | 答案是"哪一条"而不是"哪一段"，可溯源 |
| BM25 | 稀疏检索，字面精确匹配 | 「第X条」「AQ1038」这类**指称性**查询一击必中 |
| 向量检索 | 稠密语义匹配（可选） | 「井下能不能存汽油」这种**口语化**提问补位 |
| RRF 融合 | `score = Σ 1/(k+rank)`，k=60 | 两路结果合并，互不压制 |
| 条款精确路 | 中文数字转整数后与索引条号严格比对 | 解决分词把条号切碎导致的漏召回 |
| 多样性重排 | 同一文件在 Top-N 中限占半数 | 避免答案被同一本解读刷屏 |

## 三、快速开始

```bash
pip install -r requirements.txt

# 1) 扫描语料，看哪些能读、哪些要 OCR
python tools/scan_corpus.py

# 2) 抽取文本（跳过 OCR 的快速版）
python -m src.extract --no-ocr

# 3) 构建条文索引
python -m src.build_index

# 4) 跑 30 题自测
python -m src.eval

# 5) 启动界面
python -m streamlit run app/streamlit_app.py
```

增量扩充：把新标准丢进 `raw/`，重跑 2、3 两步即可；已抽取的文件会自动跳过。

### 只有代码、没有原始标准文件也能体验

仓库随附 717 条样本语料（38 份核心标准，902 KB）：

```bash
# config.yaml 里改一行
project:
  clauses_file: sample_clauses.jsonl
python -m streamlit run app/streamlit_app.py
```

> 完整的 5.6 万条语料由本地的矿山安全标准原文构建，**标准文本受版权约束，不随仓库分发**。
> 复现完整索引：把标准文件放进 `raw/`，按上面的步骤 1–3 跑一遍。会自动跳过。

## 四、语料实况（本项目最大的工程难点）

对 1084 份候选文档的实际扫描结果：

| 类别 | 数量 | 处理方式 |
|---|---|---|
| 可直接抽取文本 | 85 | 直接入库 |
| 扫描件（无文本层） | 423 | RapidOCR 逐页识别 |
| CID 字体乱码 | 少部分 | 同上 |
| `.doc` 二进制 | 一批 | OLE 复合文档流兜底解析 |

结论：**工业领域的 PDF，一半以上拿不到干净文本**。解析器必须内建质量判定和 OCR 兜底，不能直接 `pdfplumber.read()` 就进向量库 —— 这是本项目踩到的第一个坑。

OCR 速度约 1–3 秒/页（CPU），因此核心标准建议按优先级清单批量处理（`data/ocr_priority.txt`），不要一次性全量 OCR。

## 五、配置（`config.yaml`）

| 项 | 默认 | 说明 |
|---|---|---|
| `embedding.provider` | `none` | `none` 纯 BM25 离线；`local` 本地模型；`api` OpenAI 兼容接口 |
| `llm.provider` | `none` | `none` 只返回原文；配 key 后启用生成式回答并带 `[n]` 引用 |
| `corpus.enable_ocr` | `true` | 关闭则跳过扫描件 |
| `corpus.exclude_dirs` | 现场资料目录 | 内部文档不入索引 |

启用 LLM 回答（以 SiliconFlow 为例）：

```bash
export OPENAI_API_KEY=sk-xxxx
# 然后把 config.yaml 里 llm.provider 改为 api
```

## 六、实测指标

30 道煤矿专业问题（覆盖运输 / 供电 / 通风 / 提升 / 爆破 / 防治水 / 隐患判定 / 智能化），由 `python -m src.eval` 自动评测：

| 指标 | 命中率 |
|---|---|
| Top-1 | 83.3%（25/30） |
| Top-3 | 96.7%（29/30） |
| Top-5 | 100%（30/30） |

明细见 `data/eval_report.md`。每次调整检索策略都能重跑，形成回归基线。

> 说明：这是**检索层**指标，不含大模型改写。系统的定位是"把原文找出来"，而非"替标准说话"。

当前语料规模：**1084 份候选 → 591 份入库 → 56,565 条条文 → 3,000 万字**，覆盖 105 项标准号。
其中 9 份核心标准（`AQ 1038`《架空乘人装置安全检验规范》、《煤矿井下供电的三大保护细则》、`GB 51145` 电气安装验收规范 等）原为扫描件，经 OCR 后才入库——它们贡献了约 1 万条条文。

这不是课程作业，是工作里被逼出来的。在井下查一条标准，要翻三本规程、找半天页码，回头还得跟人解释「这是《煤矿安全规程》第几百几十几条」。所以才做了这套东西：问一句话，直接给原文和出处。
